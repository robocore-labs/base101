# base101_control

`ros2_control` configuration and bringup for the base101 **in sim**. Owns the
controller_manager configs, the `twist_mux` priority table, and the
hardware-overlay xacro. Configuration only — the launches that consume it
live in `base101_bringup_gazebo` and `base101_bringup_hw`.

Real hardware has no `ros2_control` at all anymore — the Axon 2 firmware owns
the whole control loop itself over zenoh (see HARDWARE.md) — so only
`twist_mux.yaml` and `base101.hardware.xacro` (now just the plain URDF, no
`<ros2_control>` block) are shared with the hardware bringup; `controllers.hw.yaml`
is gone.

## What's here

```
config/
├── controllers.sim.yaml            # wheels + arm, every configuration, one file
└── twist_mux.yaml                  # /cmd_vel priority table

urdf/
└── base101.hardware.xacro          # wraps base101.xacro with simulator:=none
```

`controllers.sim.yaml` declares the arm controllers alongside the wheel ones.
Declaring a controller only makes it spawnable by name, so an armless robot
never spawns them and the extra entries cost nothing.

## /cmd_vel routing

`twist_mux` arbitrates between Twist sources by priority, with
`use_stamped: true` (see `config/twist_mux.yaml`) — inputs (`/cmd_vel_joy`
etc.) and output are both `geometry_msgs/TwistStamped`.

In sim the output lands on `/diff_drive_controller/cmd_vel`
(diff_drive_controller in Jazzy is stamped-only). On real hardware there's no
diff_drive_controller — `cmd_vel_out` remaps to `/link101/cmd_vel`, straight
to the Axon 2 firmware, which also subscribes `TwistStamped` (confirmed
against base101-fw), so no `use_stamped` override is needed on that launch.

| Source | Topic | Priority |
|---|---|---|
| Joystick (rosboard teleop card, base101_teleop_web) | `/cmd_vel_joy` | 100 |
| Keyboard | `/cmd_vel_key` | 90 |
| Robocore agent (sim; hardware not wired up yet — see root README) | `/cmd_vel_agent` | 50 |
| Navigation (Nav2, via `base101_autonomy` on hardware) | `/cmd_vel_nav` | 10 |

Higher priority wins; lower-priority commands are timed out at 0.5s.

## Sim vs hardware

`ros2_control` (this package's `controllers.sim.yaml`) only runs in sim
(Gazebo, MuJoCo). What changes there is the SystemInterface that owns the
joints:

| Backend | Plugin | URDF generated by |
|---|---|---|
| Gazebo | `gz_ros2_control/GazeboSimSystem` | `base101_description/urdf/base101.xacro` with `simulator:=gazebo` |
| MuJoCo | `mujoco_ros2_control/MujocoSystem` | same, with `simulator:=mujoco` |
| Real HW | none — Axon 2 firmware owns locomotion + odometry itself, over zenoh | `urdf/base101.hardware.xacro` |
| Isaac Sim | — | OmniGraph drives joints natively, no ros2_control |

So `controllers.sim.yaml` works as-is for both Gazebo and MuJoCo; they just
bind to different hardware plugins. Isaac Sim ignores this config — see
`base101_isaac` for its routing. Real hardware ignores it too, entirely.

**The arm is sim-only.** The Axon 2 firmware has no arm control path yet, so
there is nothing for an arm to claim on the real robot.
`base101_bringup_hw` refuses `arm:=true` for that reason — see
[`docs/findings-open.md`](../../../docs/findings-open.md) #3.

## Real-hardware bringup

```bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 launch base101_bringup_hw robot.launch.py
```

Start the host zenoh router and `rmw_zenoh` first — see
[`HARDWARE.md`](../../../HARDWARE.md).

## Keeping wheel geometry in sync

`wheel_separation` and `wheel_radius` are duplicated across:

- `config/controllers.sim.yaml`
- `base101_mujoco/scenes/*.xml`
- `base101_isaac/launch/isaac.launch.py` (the `WHEEL_GEOMETRY` dict)
- base101-fw's own locomotion config, on the firmware side

If you tweak one, tweak all four. There's no single source of truth
today because each backend wants the numbers in its own format.
