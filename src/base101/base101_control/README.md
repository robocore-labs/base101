# base101_control

`ros2_control` configuration and bringup for the base101. Owns the
controller_manager configs, the `twist_mux` priority table, and the
hardware-overlay xacro. Configuration only — the launches that consume it
live in `base101_bringup_gazebo` and `base101_bringup_hw`.

## What's here

```
config/
├── controllers.sim.yaml            # wheels + arm, sim only (Gazebo/MuJoCo)
└── twist_mux.yaml                  # /cmd_vel priority table (sim + hw)

urdf/
└── base101.hardware.xacro          # wraps base101.xacro with simulator:=none;
                                    # no ros2_control block — see below
```

`controllers.sim.yaml` declares the arm controllers alongside the wheel ones.
Declaring a controller only makes it spawnable by name, so an armless robot
never spawns them and the extra entries cost nothing. There is no
`controllers.hw.yaml` — real hardware doesn't run ros2_control at all.

## /cmd_vel routing

`twist_mux` arbitrates between three Twist sources by priority. Inputs are
plain `geometry_msgs/Twist`.

| Source | Topic | Priority |
|---|---|---|
| Joystick (rosboard teleop card, base101_teleop_web) | `/cmd_vel_joy` | 100 |
| Keyboard | `/cmd_vel_key` | 90 |
| Navigation (Nav2) | `/cmd_vel_nav` | 10 |

Higher priority wins; lower-priority commands are timed out at 0.5s. The
output differs by backend, both set at the launch level (not in this shared
yaml):

- **Sim** — `geometry_msgs/TwistStamped` on `/diff_drive_controller/cmd_vel`
  (diff_drive_controller in Jazzy is stamped-only).
- **Real hardware** — plain `geometry_msgs/Twist` on `/cmd_vel`, which the
  Axon 2 firmware subscribes to directly. `base101_bringup_hw` overrides
  `use_stamped: false` on the twist_mux node rather than editing this file.

## Sim vs hardware

`diff_drive_controller` runs in sim (Gazebo, MuJoCo) only. What changes
between the two sim backends is the ros2_control SystemInterface that owns
the joints; real hardware has no ros2_control in the picture at all:

| Backend | Plugin | URDF generated by |
|---|---|---|
| Gazebo | `gz_ros2_control/GazeboSimSystem` | `base101_description/urdf/base101.xacro` with `simulator:=gazebo` |
| MuJoCo | `mujoco_ros2_control/MujocoSystem` | same, with `simulator:=mujoco` |
| Real HW | none — the Axon 2 firmware owns locomotion directly over zenoh (`/cmd_vel` in, `/odom` out) | `urdf/base101.hardware.xacro` |
| Isaac Sim | — | OmniGraph drives joints natively, no ros2_control |

So `controllers.sim.yaml` works as-is for both Gazebo and MuJoCo; they just
bind to different hardware plugins. Isaac Sim ignores this config — see
`base101_isaac` for its routing.

**The arm is sim-only, full stop, on real hardware.** There is no ros2_control
at all on real hardware — locomotion is bypassed entirely in favor of the
firmware's native `/cmd_vel`/`/odom` — so there is nothing for an arm
controller to claim either. `base101_bringup_hw` refuses `arm:=true` for that
reason — see [`docs/findings-open.md`](../../../docs/findings-open.md) #3.

## Real-hardware bringup

```bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 launch base101_bringup_hw robot.launch.py
```

Start the host zenoh router and `rmw_zenoh` first — see
[`HARDWARE.md`](../../../HARDWARE.md).

## Keeping wheel geometry in sync

`wheel_separation` and `wheel_radius` are duplicated across:

- `config/controllers.sim.yaml`
- `base101_mujoco/scenes/*.xml`
- `base101_isaac/launch/isaac.launch.py` (the `WHEEL_GEOMETRY` dict)
- the Axon 2 firmware's `axon_config.h` (real hardware — it now computes
  `/odom` itself, so the host no longer carries a hardware copy of these
  numbers at all)

If you tweak one, tweak the rest. There's no single source of truth
today because each simulator (and the firmware) wants the numbers in its
own format.
